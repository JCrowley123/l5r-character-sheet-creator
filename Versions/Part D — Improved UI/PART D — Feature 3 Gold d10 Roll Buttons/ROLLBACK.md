# PART D — Feature 3 · Gold d10 Roll Buttons

Part D is the UI and presentation line of work. This folder is **Feature 3**: the
sheet's roll buttons carry the same faceted gold d10 the floating manual dice-tray
button uses, instead of a game-die emoji on a gold pill.

Built on Feature 2.1. Two new files, `dice-icons.css` and `dice-icons.js`; nothing
else differs.

---

## What changed

Four buttons in the sheet drew a game-die emoji on a gold pill:

| Button | Where it comes from |
|---|---|
| `.dice-btn.sk-roll` | skill roll — built per row by the sheet's script |
| `.dice-btn.wp-roll-btn` | weapon attack — built per row |
| `.dice-btn.wp-dmg-btn` | weapon damage — built per row |
| `#btnRollInitiative` | Roll Initiative — static markup, in the Combat section |

All four now carry the d10 from `#floatingDiceBtn`: five gold facets, a paper
outline, white facet edges and a "10" in the top face.

The first three were the ones asked for. Initiative was included on request — it is
the only other game-die button in the sheet, and leaving it as the lone emoji beside
three gold dice would have looked like an oversight.

## Why this needed JavaScript

Three of the four buttons are generated by the sheet's own script whenever the
skills or weapons tables re-render, and **the sheet's script is byte-identical to
the trunk by build invariant**, so the emoji cannot be edited out at the source.

CSS could paint a die over the emoji with a data-URI background image, but a data
URI is a separate document: `var(--gold)` and the sheet's Shippori Mincho face do
not reach inside it. The icon would have to hardcode all five golds and would
quietly drift out of step the day the palette is retuned, and the "10" would fall
back to a generic serif.

Cloning the live SVG node avoids all of that. Measured in a browser, the five facet
fills on a swapped button resolve to exactly the same five values as the floating
button's — `rgb(200,168,106)`, `rgb(169,132,63)`, `rgb(138,106,53)`,
`rgb(124,94,46)`, `rgb(110,82,39)` — because the clone is in the same document and
reads the same custom properties. Retune the palette and every die follows.

`#floatingDiceBtn` is the single source of the artwork. It is read, never modified.

## Two details worth knowing

**The buttons lost their gold pill.** A gold die on a gold pill is invisible, so
`.dice-btn[data-d10]` is transparent and borderless. That is also what makes these
read as the same control as the floating dice button — an icon on the page rather
than a filled chip. The sheet's own `.dice-btn:hover{opacity:.85}` is still the
whole hover treatment; no scale or transition was added, in line with this
project's standing decision against unprompted micro-interactions.

**The accessible name changed for the better.** The emoji was previously each
button's accessible name, which a screen reader announces as "game die". Each
button already carried a useful `title`, so `dice-icons.js` copies it to an
`aria-label` before removing the emoji. Measured after the swap:

    Roll Trait+Rank, keep Trait (Unskilled: roll and keep Trait)
    Roll Initiative: Reflexes + Insight Rank, keep Reflexes
    Roll attack
    Roll damage

## Rollback

**Each half is a single file, and the splice is file-guarded.**

| To drop | Delete | Then |
|---|---|---|
| the whole feature | `dice-icons.js` | `python splice_swipe_tabs.py` |
| the styling only | `dice-icons.css` | `python splice_swipe_tabs.py` |

Deleting the script alone is a complete rollback: every CSS rule is keyed on
`[data-d10]`, which only `dice-icons.js` ever sets, so the stylesheet goes inert and
the buttons keep the sheet's own gold pill and emoji. That is also what a visitor
with scripting turned off sees — the feature degrades to exactly the sheet the trunk
ships.

**Or delete this whole folder**, and you are back to
`PART D — Feature 2.1 Ring DOM Order, Void Card Fit and Harness Fixes`, the previous
build, fully working.

This folder reads the read-only trunk directly and writes only to itself.

## Verified

Measured in a real browser engine against the shipped file. Every build invariant
still holds:

- the sheet's own `<script>` byte-identical to the trunk, all 807,671 characters
- 209 original element IDs preserved, none missing, none duplicated
- 10 sections, 16 `.roll-modal-overlay` blocks, tag balance clean
- the trunk still hashes `bfbbd19197c9fd81` — never opened for writing

The feature:

- **all four buttons carry the die, zero emoji left.** On load one button exists
  (Initiative) and is swapped; after adding a skill row and a weapon row there are
  four, all four swapped. That second step is the important one — it is the
  `MutationObserver` path covering rows the sheet builds at run time.
- **exactly one `<svg>` per button.** Appending the icon re-triggers the observer,
  so the `data-d10` guard has to make the second pass a no-op. It does.
- **the die matches the floating button** facet for facet: same five resolved gold
  fills, and the clone carries the `<text>` reading `10`.
- **no layout shift.** Skill row 58.3px and weapon row 42.5px, identical to Feature
  2.1. The button goes from 35.5x27.6 to 28x28 — narrower, same row height.
- **touch targets intact.** With the coarse-pointer rules on, the button is 40x40
  with the 20px die centred to within a pixel on both axes.
- **the sources are untouched:** the floating button and both dice-picker dice are
  still present and unmodified. No JavaScript errors.
- **no regression.** The carousel harness scores 31/35, identical to Feature 2.1,
  failing the same four assertions. Ring geometry re-measured: breakpoint exact at
  599/600px, zero overlaps and zero escapes at Void ranks 2 and 10, document and
  focus order still clockwise.

### Not verified here

- Appearance. Everything above is measurement — nobody has looked at a 20px die on
  screen yet, and whether the facets and the "10" read well at that size is a
  judgement a browser cannot make. This is the first thing to check on the desktop.
- Print. The sheet's own print block already hides `.dice-btn` outright, and
  `#btnRollInitiative` carries that class, so there should be nothing to see — but
  no one has printed it.
- The four carousel assertions the environment cannot run, as for Feature 2.1:
  headless Chrome under a virtual time budget fires no `scroll` or `scrollend`
  events, and those tests depend on them.
